# Tdyssey pushing data for image world models

Continuous PushT pushing episodes on five letters (T, near-T, Y, D, L), with the exact
camera image at every step. Made for training a model that takes **image(s) + action**
and predicts **the next image**. Everything was generated by machines in the official
simulator: no human demonstrations.

## Quick start

```bash
tar -xzf tdyssey_pushing_data.tar.gz && cd tdyssey_pushing_data
python scripts/load_example.py .        # numpy only; loads one file and prints a summary
```

In your training code:

```python
import sys; sys.path.insert(0, "scripts")
from load_example import load_pairs
train, val = load_pairs(".", parts=["part0", "planner/"], history=1)
# train["image"] (N, 1, 96, 96, 3) uint8, train["action"] (N, 2), train["next_image"] (N, 96, 96, 3) uint8
```

`load_pairs` holds out whole scenes for validation, can return a longer image history
(`history=2` gives frames t-1 and t, like the Diffusion Policy's input), and can keep only
steps with contact (`contact_only=True`).

## What is in the package

```
data/base_policy/part*.npz       states, actions, contacts per step (2000 episodes)
data/planner/<letter>-<k>.npz    same format (planner episodes)
frames/<source>/<name>_frames.npz  frames[i, t] = camera image (96x96 RGB uint8) of data episode i, step t
scripts/load_example.py          builds (image, action, next image) examples; numpy only
scripts/replay_frames.py         regenerates the frames (e.g. at another resolution); needs the Tdyssey repo
```

## How the arrays line up

For episode `i`, with `n = mask[i].sum()` valid steps (n ≤ 301):

| Array | Shape | Meaning |
| --- | --- | --- |
| `frames[i, t]` | (96, 96, 3) uint8 | camera image at step t (exactly what the official env returns as `obs["image"]`, scaled to 0-255) |
| `state[i, t]` | (9,) float32 | object x, y (px), angle (rad), object vx, vy (px/s), angular velocity (rad/s), pusher x, y (px), goal angle |
| `pusher_velocity[i, t]` | (2,) | pusher vx, vy (px/s) |
| `action[i, t]` | (2,) float32 | pusher **target** (px) sent at step t; it moves state/frame t to t+1 |
| `contacts[i, t+1]` | int | contact points between pusher and letter during step t (0 = no contact) |
| `coverage[i, t]` | float | fraction of the goal covered by the letter (success when > 0.95) |
| `mask[i, t]` | bool | step exists; rows after the end of the episode are zeros |
| `shape[i]`, `seed[i]`, `success[i]` | | letter, scene seed, whether the episode succeeded |

So a training example is `(frames[i, t], action[i, t]) -> frames[i, t+1]` for `t = 0 .. n-2`.
An episode ends early when the letter covers more than 95% of the goal; otherwise it runs
300 steps.

Conventions:
- Simulator frame is 512 x 512 px; image pixel = simulator px x 96/512. The goal (green
  outline) is fixed for each letter.
- Control is 10 Hz. The action is a target point, not a velocity: the pusher follows it with
  the simulator's PD controller over 10 physics substeps, so it does not jump to the target.
- The images contain no target marker (the official env draws it only on its display copy).
  At contact, the simulator also draws small contact markers into the image, as in the
  official observations; that is why the frames were made by replaying the physics rather
  than by drawing each pose.
- Positions are the physics body positions used by the official env (`env.block.position`,
  `env.agent.position`).

## Correctness checks done

- Every frame was produced by replaying the recorded actions in the official simulator
  from the recorded scene; at every step the replayed object and pusher poses matched the
  record (largest difference about 2e-5 px, float32 storage), otherwise generation stopped.
- Frames equal the simulator's own `obs["image"]` at that step (same code path).

## Advice for using it

- **Split by scene, not by frame.** Nearby frames are almost identical; a random frame split
  leaks. Each base-policy scene seed was run for all five letters, so hold out seeds
  (`load_pairs` does this).
- **Do not train on our test scenes.** These seed ranges are our evaluation sets:
  300000-319980, 400000-419980, 900000-919980, and everything from 2000000 to 5199980.
  This package uses 604000-611980 (base policy) and 6000000-6001980 (planner) only.
- **Contact is where the difficulty is.** Only about a third of steps involve contact. Consider
  oversampling contact windows (at least half of each batch) and reporting errors on contact
  steps separately.
- **Shape-aware evaluation.** The exact poses (`state`) let you check predictions beyond pixel
  error: e.g. overlap between the predicted and true letter masks, or fit the letter's pose to
  the predicted image and compare with `state[i, t+1]`. Rounded or distorted letters show up
  clearly in mask overlap and corner positions, while average pixel error hides them.

## How much data

The base-policy set has about 580,000 transitions, of which about 36% involve contact;
the planner set adds about 99,415 transitions. Its D and Y episodes mostly reach the goal; on
T, near-T and L it often stalls just short of the goal while moving around the letter, so only
8-15% of its steps on those letters involve contact (33% on D).
For reference, an earlier image world-model run on this project used about 1 million
transitions (74% with contact), and our state world model learned the dynamics from 1,500
of the base-policy episodes (about 430,000 transitions). More data of either kind (or more letters) can be generated in under
an hour on one GPU if needed.

## Where the data came from

- **Base policy** (`data/base_policy`): the frozen official RSS 2023 Diffusion Policy
  checkpoint for PushT (trained on T), run on all five letters from the same starting scenes,
  with Gaussian noise added to its actions for variety: 0, 10, 25 and 50 px (two files each,
  `part*-noise<σ>`). It mostly fails on D and L, so those episodes are long, non-expert
  pushing.
- **Planner** (`data/planner`): our world-model planner, which reads the exact simulator
  state (privileged information) and plans pushes with a learned state world model. It reaches
  the goal on 97/100 D and 70/100 Y scenes, but only 12-29/100 on T, near-T and L, where it
  tends to stall near the goal. It adds deliberate pushes, travel around the letter, and many
  states close to the goal, which the base-policy set rarely reaches on D and L.

## Regenerating frames (optional)

Only needed for another image size. From the root of the Tdyssey repository with its Python
environment (it uses `tdyssey/` and `third_party/diffusion_policy`):

```bash
python /path/to/tdyssey_pushing_data/scripts/replay_frames.py \
    /path/to/tdyssey_pushing_data/data/base_policy/part0-noise0.npz part0-noise0_frames_128.npz --size 128
```
